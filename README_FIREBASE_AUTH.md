# Firebase Authentication & SMS Audit Architecture for ePaper

This document outlines the end-to-end architecture, configuration, and operation of multi-tenant Firebase Authentication (Google OAuth, Phone SMS OTP, and Email Link Verification) across both **Stage 1 (Publishers)** and **Stage 2 (Readers)** in the ePaper platform.

---

## 1. Architectural Highlights & Why No `firebase-admin`

Cloudflare Workers run on the V8 isolate runtime, which does not natively support Node.js gRPC modules or full Node filesystem APIs. As a result, the standard Node.js `firebase-admin` package cannot run inside Cloudflare Workers (`workers/admin` and `workers/content`).

Instead, we use a **Lightweight Edge Verification Pattern**:
1. **Frontend (`frontend/tenant-portal`)**: Uses the standard `@firebase/auth` and `@firebase/app` client SDK to perform browser-side interactions (`signInWithPopup` for Google, `signInWithPhoneNumber` with invisible `RecaptchaVerifier` for Mobile SMS, and `applyActionCode` for verification emails).
2. **Backend Workers (`workers/admin` & `workers/content`)**: Receive the raw Firebase `idToken` generated by the frontend. Using `jose`, the Workers fetch Google's public JSON Web Key Set (JWKS) directly from `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com`, cache the public keys in memory and Cloudflare edge Cache (`caches.default`), and verify the token's RS256 signature, expiry, audience (`FIREBASE_PROJECT_ID`), and claims at the edge without querying Firebase servers.
3. **Stateless Session Issuance**: Once the Firebase token is verified, the Worker creates or resolves the corresponding publisher or reader account in SQLite (D1) and issues the platform's standard **signed HTTP-only session cookies / JWTs**. All subsequent requests use this internal stateless session, guaranteeing zero KV or DB lookups on every route request.

## 2. Two-Stage Auth Flows

### Stage 1: Publisher Portal (`portal.epaperspace.com`)
- **Login / Signup UI**: Located at `/login` (`OrgLoginPage.tsx`) and `/signup` (`SignupPage.tsx`).
- **Options Supported**:
  - **Google OAuth**: One-click Google sign-in.
  - **Mobile SMS OTP**: E.164 phone number verification (`PhoneAuthForm.tsx`) protected by Google reCAPTCHA.
  - **Email & Password**: Standard password auth with optional Firebase verification emails.
- **Verification Routing**: `workers/admin/src/firebase-auth.ts` validates the token and resolves the organization workspace or creates a new one (`/api/auth/verify-org`).

### Stage 2: Reader Tenant Portals (`{slug}.epaperspace.com`)
- **Reader Auth UI**: Located in `ReaderAuthDialog.tsx` modal overlay when a reader tries to access paid or gated ePaper editions.
- **Options Supported**:
  - **Google OAuth**: Fast reader login.
  - **Mobile SMS OTP**: Reader phone verification (`PhoneAuthForm.tsx stage="reader"`).
  - **Email & Password**: Traditional reader account creation.
- **Verification Routing**: `workers/content/src/reader.ts` (`/api/read/:slug/verify-firebase`) validates the Firebase token and queries `getTenantDb(slug)` to resolve or provision the reader inside the tenant's isolated D1 database (`epaper-${slug}`).

## 3. Centralized Email Verification (`/auth/action`)

To avoid setting up individual custom SMTP configurations, DNS SPF/DKIM records, or separate Firebase Action domains for every tenant subdomain (`{slug}.epaperspace.com`), the platform uses **Single Subdomain Verification**:
- All Firebase out-of-band email links (Password Reset, Email Verification) point to the main portal domain: `https://portal.epaperspace.com/auth/action?mode=verifyEmail&oobCode=...`
- **`FirebaseAuthActionPage.tsx`** handles these links:
  1. Validates the `oobCode` via `applyActionCode(auth, oobCode)`.
  2. Reloads the Firebase user profile (`user.reload()`) to force a fresh `getIdToken(true)` containing the updated `email_verified: true` claim.
  3. Checks `localStorage` or URL parameters (`returnUrl`) to redirect the verified user or reader back to their specific tenant portal or publisher dashboard cleanly.

## 4. SMS Quota Audit & Rate Limiting

To prevent SMS pumping attacks, bot abuse, and excessive Firebase billing on Mobile OTP:
1. **Frontend Cooldown & reCAPTCHA**: `PhoneAuthForm.tsx` enforces an invisible `RecaptchaVerifier` guarded by `useRef` (so it only initializes once per component lifecycle) and enforces a 60-second cooldown timer before resending OTP.
2. **Backend IP Rate Limiting**: `workers/admin/src/firebase-auth.ts` enforces a strict per-IP rate limit (maximum 5 SMS attempts per hour).
3. **SMS Audit Table (`sms_audit_log`)**: Every OTP send attempt reports to `POST /api/auth/audit/sms-send`. The backend logs the attempt into the `CONTROL_DB` (`sms_audit_log` table):
   ```sql
   CREATE TABLE IF NOT EXISTS sms_audit_log (
     id TEXT PRIMARY KEY,
     phone_masked TEXT NOT NULL,
     stage TEXT NOT NULL,       -- 'publisher' or 'reader'
     tenant_slug TEXT,          -- null for publisher, slug for reader
     ip_address TEXT,
     status TEXT NOT NULL,      -- 'SENT' or 'FAILED'
     created_at TEXT NOT NULL DEFAULT (datetime('now'))
   );
   ```

## 5. Environment Configuration & Setup

### Frontend Environment Variables (Vite / Cloudflare Pages)
Add the following to your `.env` or Cloudflare Pages environment variables (`frontend/tenant-portal`):
```env
VITE_FIREBASE_API_KEY=AIzaSy...
VITE_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-project-id
VITE_FIREBASE_STORAGE_BUCKET=your-project.appspot.com
VITE_FIREBASE_MESSAGING_SENDER_ID=1234567890
VITE_FIREBASE_APP_ID=1:1234567890:web:abcdef...
```

### Backend Secrets (`workers/admin` & `workers/content`)
Set `FIREBASE_PROJECT_ID` inside your Cloudflare Workers environment using `wrangler`:
```bash
# Set for Admin Worker
npx wrangler secret put FIREBASE_PROJECT_ID --name epaper-worker-admin
# (Enter your Firebase Project ID, e.g., your-project-id)

# Set for Content Worker
npx wrangler secret put FIREBASE_PROJECT_ID --name epaper-worker-content
# (Enter your Firebase Project ID, e.g., your-project-id)
```
Or define it inside `wrangler.toml` under `[vars]`:
```toml
[vars]
FIREBASE_PROJECT_ID = "your-project-id"
```

## 6. Provider Swapping & Extension

If you need to add or swap authentication providers in the future (e.g., Apple Auth, GitHub Auth, SAML/SSO):
1. **Enable in Firebase Console**: Go to Firebase Authentication -> Sign-in method -> Add provider.
2. **Frontend Initialization**: In `frontend/tenant-portal/src/lib/firebase.ts`, export the new provider:
   ```ts
   export const appleProvider = new OAuthProvider('apple.com');
   ```
3. **Connect to UI**: Call `signInWithPopup(auth, appleProvider)` inside `SignupPage.tsx`, `OrgLoginPage.tsx`, or `ReaderAuthDialog.tsx`.
4. **Backend Zero-Change Guarantee**: Because all Firebase-issued `idTokens` follow the exact same JWT specification and are signed by Google's JWKS, **no backend code changes are needed when enabling new OAuth providers via Firebase**. The worker (`verifyFirebaseToken.ts`) automatically validates the token and extracts `sub` (uid), `email`, and `name`!
